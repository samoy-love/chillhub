# Backlog (Launcher + Servers)

## Блокеры релиза

Задачи, без которых релиз выпускать нельзя. Порядок — по приоритету.
Статус на 2026-08-01: открыты **B3** и **B8**, остальные закрыты.

### ~~B1. Бесконечный цикл самообновления лаунчера~~ — ЗАКРЫТО
Лаунчер предлагал обновление при каждом запуске и обновлялся «сам на себя» (`1.1.7 → 1.1.7`), каждый раз полностью себя перекачивая.

Причина: множество файлов, по которым принималось решение об обновлении, пересекалось с `--preserve`, который апдейтер отказывается перезаписывать. `launcher.version` — апдейтер пишет его сам (`Encoding.UTF8` с BOM, 10 байт против 8 в манифесте). `config.json` — расходился после первого запуска игры (сохранение `LastGameId`). Усугублялось тем, что каталог установки `%LOCALAPPDATA%\ChillHub` совпадал с каталогом пользовательского конфига.

Что сделано:
- конфиг и логи переехали в `%APPDATA%\ChillHub` с одноразовой миграцией (`ConfigService.MigrateLegacyConfig`);
- preserve‑правила вынесены в единый `PreserveMatcher` (`updater/UpdatePreserve.cs`), общий для лаунчера и апдейтера; preserve‑файлы и артефакты апдейтера исключены и из сравнения, и из скачивания;
- служебные файлы апдейтера (`filelist.txt`, `deletelist.txt`, `emptydirs.txt`, `apply-update.log/.cmd`, каталог `updater\`) вычищаются из папки установки;
- добавлен предохранитель `updater/tests/ManifestPreserveCheck`: падает, если файл из preserve‑списка попал в манифест лаунчера.

Осталось (не блокер): подключить `ManifestPreserveCheck` в CI‑workflow — сейчас он запускается вручную.

### ~~B2. Path traversal в новостных эндпоинтах админки~~ — ЗАКРЫТО
Защита вынесена в `server/internal/adminutil` (`IsSafeGameID`, `IsSafeVersion`, `IsSafeNewsSlug`, `NewsSlugPath`, `EnsureWithin`, `SanitizeFilename`, `SanitizeAssetPath`) и применяется во всех доменных пакетах; дублировать её у себя пакетам запрещено. Есть тесты (`adminutil_test.go`, `news_test.go`).

### B3. Текст чужой песни в бинаре — ОТКРЫТО
В `launcher/ChillHub/MainWindow.xaml.cs` (метод `InitKaraokeLyrics`) по‑прежнему захардкожен полный текст чужой композиции, печатается бегущей строкой в шапке. Юридический блокер. Удалить вместе с механикой караоке и постоянно тикающим `DispatcherTimer`.

### ~~B4. Инбокс обратной связи не держит нагрузку~~ — ЗАКРЫТО
Введены жёсткие лимиты (`server/internal/adminapi/feedback`): `MaxLogBytes` 256 КиБ на вложенные логи, `MaxItems` 2000 обращений, `MaxTotalBytes` 64 МиБ на файл, подрезка (`Prune`). Публичный `/feedback/submit` ограничен 5 запросами в минуту на адрес клиента (`server/internal/ratelimit`, лимитер чистит протухшие записи). Автоотправка отчётов об ошибках отключается настройкой «Конфиденциальность» в лаунчере (`AppConfig.AutoErrorReports`).

### ~~B5. Неатомарная активация версии сборки~~ — ЗАКРЫТО
Потоковая и чанковая загрузки распаковывают ZIP в стейдж‑каталог на том же томе (`stageVersionDir`) и подменяют каталог версии одним `rename` только после полной распаковки и подсчёта хешей. Примечание: устаревший `POST /admin/api/upload` (простой multipart, UI им не пользуется) по‑прежнему распаковывает напрямую в `content/{gid}/{ver}/files` — при желании стоит либо перевести на стейдж, либо удалить.

### ~~B6. Персональные данные в git~~ — ЗАКРЫТО
`content/feedback/inbox.json` снят с отслеживания (`git ls-files content/feedback` пуст). Вопрос очистки истории решается отдельно.

### ~~B7. Довести и закоммитить security-хардинг~~ — ЗАКРЫТО

## Режим технических работ

> Статус: реализовано. Сервер — `server/internal/maintenance/` (публичный `GET /api/maintenance`,
> админские `/admin/api/maintenance/{get,set,clear}`, состояние в `content/maintenance/state.json`).
> Клиент — `Core/Maintenance/MaintenanceService.cs` (опрос раз в 60 с, баннер, блокировки,
> автоснятие). Окно активности считает сервер, поэтому автосброс работает без перезапуска клиента.
> Спецификация — `Documentation.md` §7 и §8.5.

- Флаг с сервера включает режим: блокирует установку/обновление/запуск (или только часть, по параметрам сервера).
- Пользователь видит баннер с причиной и ETA завершения.
- После окончания — автоматическое возвращение к нормальному режиму без перезапуска клиента.

Критерии: режим включается/выключается по API, баннер отображается, кнопки корректно блокируются, логика автосброса работает.

## Метрики и алерты (минимальные требования)

> Статус: сделана серверная часть по клиентским метрикам — `server/internal/metrics/`
> (`POST /metrics/report`, `GET /admin/api/metrics/summary`, `POST /admin/api/metrics/clear`,
> хранение `content/metrics/events.jsonl` с ротацией), плюс раздел в админке.
> Спецификация и список того, что осознанно НЕ собирается, — `Documentation.md` §8.6.
>
> НЕ сделано: отправка событий из лаунчера (клиентской части нет, поэтому сводка пуста);
> серверные метрики RPS/latency/4xx/5xx; метрики nginx, статики, деплоя и инфраструктуры;
> алерты в Telegram. Пункты ниже сохранены как есть.

- **Лаунчер (клиент)**
  - DAU/MAU; число запусков клиента.
  - Установки/обновления игр (шт/день, байты скачивания, средняя скорость, ошибки/откаты).
  - Время установки/обновления; процент успешных операций.
  - Ошибки (коды + контекст), падения; версия клиента.

- **API/Сервер**
  - HTTP RPS, p50/p95/p99 latency по endpoint’ам.
  - 4xx/5xx в разрезе endpoint/версии.
  - Health/ready флаги, пулы соединений к БД, ошибки БД.

- **Nginx/прокси**
  - RPS, 4xx/5xx, upstream latency, size ответов, кеш‑хиты (если есть), сертификаты (срок жизни).

- **Статика/скачивание**
  - Отдача файлов: bytes served, скорость, ошибки/обрывы.
  - Топ загружаемых ресурсов; хэши манифестов (верификация).

- **Деплой**
  - Успех/неуспех шагов, длительность, версия релиза/коммита.
  - Проверки после деплоя (smoke‑tests: HTTP 200/401/302 по ключевым точкам, доступность манифестов, хэши файлов).

- **Инфраструктура** (минимально)
  - CPU/RAM/Disk/FDs по сервисам; аптайм; рестарты unit’ов.

- **Алерты в Telegram** (простые пороги)
  - API: p95 > 800ms 3мин; 5xx > 1% 3мин; Health=DOWN немедленно.
  - Nginx: 502/504 > 1% 3мин; сертификат < 14 дней — предупреждение.
  - Деплой: шаг упал; смоки не прошли.
  - Клиент: скачивания «ошибка» > N за 10мин.
  - Формат: «[sev][компонент] событие, метрика=X (порог=Y), ссылка на дашборд/логи». 

Примеры стеков: Prometheus/OpenTelemetry + Grafana; алерты → Telegram‑бот (webhook).

## Уведомления (Push/Toasts/Баннеры)

- **Новая версия лаунчера**
  - Тост: «Доступна новая версия лаунчера vX.Y. Обновить сейчас?» [Обновить] [Позже]
  - Баннер: «Мы улучшили стабильность и скорость. Обновитесь до vX.Y.» [Смотреть изменения] [Обновить]

- **Технические работы**
  - Баннер (жёлтый): «Идут техработы до HH:MM. Установка/обновление временно недоступны.» [Подробнее]
  - Тост перед началом: «Через 5 минут начнутся техработы.» [Ок]

- **Критический фикс**
  - Баннер (красный): «Критическое обновление безопасности. Рекомендуем обновиться сейчас.» [Обновить]
  - Тост: «Вышел критический фикс. Обновиться?» [Обновить] [Позже]

- **Новая сборка/контент**
  - Тост: «Новая сборка для <Игра>. Смотреть изменения?» [Открыть] [Скрыть]

Поведение:
- Тосты автоисчезающие (6–8с), с возможностью закрепить.
- Баннеры — до взаимодействия/снятия условия (например, режим техработ).
- Все кликабельные действия трекаются в метриках.
