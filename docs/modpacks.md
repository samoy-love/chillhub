## 1. Зачем

Сейчас моды зашиты внутрь сборки игры. Админ собирает набор модов в r2modman,
кладёт результат в ZIP вместе с игрой и публикует одной версией. Это значит:

- **обновить один мод = перезалить всю сборку** и заставить каждого игрока
  скачать разницу по всему дереву;
- **игру нельзя запустить без модов** — файлов ванильной игры отдельно нет;
- **Steam-копию модами не снабдить** — раздаётся только пиратская сборка целиком;
- **состав модов нигде не зафиксирован** машиночитаемо, кроме случайно
  попавшего в сборку `mods.yml` от r2modman.

После перехода сборка игры содержит только игру, модпак — только моды, и они
обновляются независимо.

### Локальные установки

`D:\Games\Lethal Company` и `D:\Games\Risk of Rain 2` — BepInEx установлен
прямо в папку игры. `doorstop_config.ini`:

```ini
[General]
enabled = true
target_assembly=BepInEx\core\BepInEx.Preloader.dll
```

`.doorstop_version` = `4.5.0` и `4.0.0`. Путь относительный, аргументов
командной строки не требуется — игра запускается двойным кликом по exe и
подхватывает моды. **Это и есть штатный способ**, на нём строится весь план.

Форматирование ini у разных сборок разное (`enabled = true` против
`enabled=true`, слэши `\` против `/`) — редактор ini обязан править только
значение, сохраняя оформление файла.

### Thunderstore API

| Что | Эндпоинт | Проверено |
|---|---|---|
| Секции комьюнити (UUID) | `/api/cyberstorm/community/{slug}/filters/` | UUID секции **свой у каждой игры** |
| Каталог | `/api/cyberstorm/listing/{slug}/?section={uuid}&ordering={o}&q={текст}&page=N` | 20 на страницу |

## 3. Принятые решения

| Решение | Выбор |
|---|---|
| Куда ставятся моды | **Прямо в папку игры**, рядом с файлами игры. Профиля нет |
| Как выключаются моды | Правка `enabled` в `doorstop_config.ini`. Аргументов не требуется |
| Конфиги модов | **Не сохраняются.** Обновление модпака возвращает настройки автора |
| Логи в обратной связи | Уходят **всегда**. Галочка и список удаляются, форма верстается заново в тех же границах |
| Кеш архивов на сервере | TTL **30 дней** по времени последнего обращения + ручная очистка |
| Что видит игрок | Название и версия модпака. Выбора нет |
| Зеркалирование | Моды скачиваются на сервер и раздаются с него |
| Один активный модпак | На игру — ровно один. Несколько собранных версий лежат рядом, активна одна |

## 4. Как работает установка модов

Никаких аргументов запуска, никаких абсолютных путей, никакого профиля.

```
D:\Games\ChillHub\lethal-company\        <- корень игры
├── Lethal Company.exe                   ─┐
├── Lethal Company_Data\                  │ манифест ИГРЫ
├── UnityPlayer.dll                       │
├── SteamFix64.dll                       ─┘
├── winhttp.dll                          ─┐
├── doorstop_config.ini                   │ манифест МОДПАКА
├── .doorstop_version                     │
└── BepInEx\                              │
    ├── core\BepInEx.Preloader.dll        │
    ├── plugins\Автор-Мод\*.dll           │
    └── config\*.cfg                     ─┘
```

`winhttp.dll` перехватывает загрузку процесса, читает `doorstop_config.ini`,
находит по относительному пути `BepInEx\core\BepInEx.Preloader.dll` и грузит
BepInEx. Всё внутри одной папки.

**Запуск с модами:** `enabled = true` → запустить exe (или Steam).
**Запуск без модов:** `enabled = false` → запустить exe. Файлы модов остаются
на диске, Doorstop их не грузит.

Из этого следует главное ограничение: **моды принадлежат папке**. Если игрок
хочет играть и в Steam-копию, и в сборку с сервера, модпак ставится в обе
папки и занимает место дважды. Лаунчер это поддерживает, но по умолчанию
ставит в ту папку, которую игрок выбрал последней.

### Как это делают другие менеджеры

Для справки, чтобы не повторять их ошибки:

- **r2modman** держит моды в отдельном профиле и передаёт
  `--doorstop-enable true --doorstop-target <абсолютный путь>`. Для ванили обе
  ветки шлют `--doorstop-enable false` — **флаг Doorstop 3**, который Doorstop 4
  (наш случай) не распознаёт.
- **r2modman для Epic/Xbox**, где аргументы до игры не доходят, правит
  `doorstop_config.ini`. Единственная его ветка, где выключение гарантировано.
- **Gale** для ванили просто не добавляет аргументы, но копирует `winhttp.dll`
  и ini в папку игры безусловно. Ваниль работает по промаху: в ini стоит
  `enabled = true` и относительный путь к preloader, которого в папке игры нет.

Наш способ — правка ini — совпадает с единственной надёжной веткой r2modman и
дополнительно переживает запуск игры мимо лаунчера, прямо из библиотеки Steam.

## 5. Сервер: модель данных

### Реестр игр

Новое поле в `games.Entry` (`server/internal/adminapi/games/games.go:26`):

```go
type Entry struct {
    // ...существующие поля
    Mods *ModsConfig `json:"mods,omitempty"`
}

type ModsConfig struct {
    Enabled       bool     `json:"enabled"`
    Community     string   `json:"community"`      // "lethal-company"
    EcosystemGame string   `json:"ecosystemGame"`  // ключ схемы; по умолчанию = Community
    SectionUUID   string   `json:"sectionUuid"`    // UUID секции "Modpacks", кеш из /filters/
    Loader        string   `json:"loader"`         // "bepinex"
    SteamAppID    string   `json:"steamAppId"`     // "1966720"
    SteamFolder   string   `json:"steamFolder"`    // "How to Fish/How to Fish"
    ExeNames      []string `json:"exeNames"`
}
```

Указатель, а не встроенная структура: у всех существующих записей поля нет, и
`omitempty` оставляет реестр байт-в-байт прежним.

**Осторожно:** `games.Save()` парсит payload обычным `json.Unmarshal` в
`Entry` — неизвестные ключи отбрасываются молча. Поле, добавленное только на
клиенте, тихо пропадёт. Заводить сразу с обеих сторон.

### Дерево на диске

```
content/manifests/_mods/{gameId}/{version}.json         манифест модпака
content/manifests/_mods/{gameId}/sources/{version}.json состав: пакет, дерево, время сборки
content/manifests/_mods/{gameId}/latest.json            активная версия
content/content/_mods/{gameId}/{version}/files/         готовое дерево модов
content/tmp/ts-cache/{full_name}.zip                    кеш архивов Thunderstore, TTL 30 дней
content/tmp/ts-cache/meta/{full_name}.json              кеш описаний версий, тот же TTL
```

Состав лежит в **подкаталоге** `sources/`, а не рядом с манифестом под именем
`{version}.src.json`, как задумывалось сначала. Список версий читает каталог
манифестов и брал `ASTeam-LethalReloaded-2.2.12.src` за отдельную версию —
призрак, который нельзя ни активировать, ни удалить.

Имя версии — **`{ns}-{name}-{version}`**, например `ASTeam-LethalReloaded-2.2.12`.
Без имени пакета версии двух разных модпаков не упорядочены и путаются. Формат
проходит `adminutil.IsSafeVersion` (буквы, цифры, `-`, `_`, `.`). Пересборка
того же — суффикс `_2`.

`_mods` под `manifests/` — та же конвенция, что у существующего `_registry`.
Три правки:

- добавить в skip-список `games.FromManifests()` (`games.go:61`);
- добавить в скан-фолбэк `loadGamesByScanning()` в `server/cmd/api/main.go`;
- запретить `_mods` и `_registry` как `gameId` в `games.Save()` — сейчас
  `_registry` тоже можно завести игрой.

nginx менять не нужно: `location ^~ /content/` и `^~ /manifests/` уже
покрывают новые подкаталоги.

### `sources/{version}.json`

```json
{
  "kind": "thunderstore",
  "version": "ASTeam-LethalReloaded-2.2.12",
  "displayName": "Lethal Reloaded",
  "package": "ASTeam/LethalReloaded",
  "packageUrl": "https://thunderstore.io/c/lethal-company/p/ASTeam/LethalReloaded/",
  "builtAt": "2026-08-27T12:00:00Z",
  "loader": "BepInEx-BepInExPack-5.4.2305",
  "tree": ["BepInEx-BepInExPack-5.4.2305", "FlipMods-TooManyEmotes-2.3.17", "..."],
  "missing": [],
  "files": 2431,
  "bytes": 1932735283
}
```

Нужен для диффа состава между версиями и для показа в админке. `kind` может
быть `thunderstore` (пакет-модпак) или `r2modman` (импорт `mods.yml`).

## 6. Сервер: конвейер сборки модпака

Один NDJSON-поток, как у `UploadProcessStream`, чтобы админка показывала
прогресс на гигабайтах.

1. **Резолв дерева.** Обход в ширину по `dependencies`, первый встреченный
   `ns-name` побеждает. `404` — «пакет удалён», строка в отчёте, не падение.
   Каждый прочитанный пакет уходит в поток событий: без счётчика обход
   выглядит зависанием.

   Отвечает на запросы **индекс сообщества**, а не API по одному пакету.
   Адрес `/c/{slug}/api/v1/package/` отдаёт все пакеты сообщества разом: для
   lethal-company это 34.5 МБ gzip (327 МБ JSON), 50 568 пакетов, 191 915
   версий — и приходит за секунду. В каждой версии лежит ровно то, ради чего
   делались полторы сотни отдельных запросов: зависимости, адрес архива и его
   размер. Тело разбирается потоком и в память целиком не попадает; готовый
   индекс живёт час.

   Чего в индексе нет — зависимость из другого сообщества — спрашивается
   поштучно: 3 одновременных запроса, темп ~3 в секунду с бэкоффом, ответы
   кешируются на диск. Неудача индекса не отменяет сборку, а возвращает её к
   прежней скорости.

   **Разбор имени.** В строке `swuff-star-ConfigurableCrafting-1.0.0` нельзя
   угадать, где кончается пространство имён: дефисы есть и там, и там. Индекс
   избавляет от догадки — он найден по полному имени версии. Для одиночных
   запросов перебираются все точки разреза, и пакет считается пропавшим,
   только когда `404` ответили все.
2. **Смета.** `HEAD` по CDN → суммарный вес. Сверка с `builds.FreeSpace`.
   Отдаётся **до** скачивания. Идёт параллельно: хост архивов — не API, и
   пасти его темпом API значит вдвое удлинить молчание перед скачиванием.
3. **Скачивание.** С `gcdn.thunderstore.io`, до шести архивов одновременно —
   у хранилища своя очередь и свой темп, лимит API к нему не относится. Кеш по
   `{full_name}.zip` — версии иммутабельны. Каждая неудачная попытка
   повторяется (пять попыток с растущей паузой) и уходит в поток событий.

   Имя объекта в хранилище выводится из полного имени пакета **не всегда**:
   длинное имя Thunderstore обрезает и приписывает случайный хвост, и
   угаданный адрес отвечает `403 AccessDenied` от бакета, а не `404`. Поэтому
   запасным адресом идёт `download_url` из метаданных пакета; пакет считается
   пропавшим, только когда не ответил ни один адрес.

   Установка при этом **последовательна** и строго в порядке плана: два пакета
   могут положить файл по одному пути, и решать, чей останется, обязано место
   в дереве зависимостей, а не то, чей распаковщик успел первым.
4. **Раскладка** по `installRules` из ecosystem schema:
   - пакет из `modloaderPackages` → содержимое его `rootFolder` в корень;
   - `trackingMethod: none` (`config`) → без подкаталога;
   - `trackingMethod: subdir` → `BepInEx/<route>/{Author}-{ModName}/`;
   - `subdir-no-flatten` → то же, но с сохранением структуры;
   - `*.mm.dll` → `monomod`; остальное → маршрут с `isDefaultLocation`.

   **Схлопывается маршрут, а не вложенность под ним.** Если архив назвал
   маршрут сам — `BepInEx/plugins/…` или просто `plugins/…`, — то всё, что
   ниже, мод кладёт осознанно: у More_Suits есть и `moresuits/Glow.png`, и
   `moresuits/advanced/glow.png`, и это разные файлы. Если маршрута в архиве
   нет и файлы лежат россыпью по папкам автора (`DLL/`, `SfDesat/`,
   `TolianMoons/` у Tolian_Moons), вот их и схлопывают в папку мода.

   Правило выведено сверкой с живой сборкой lethal-company, разложенной
   настоящим r2modman: на 60 пакетах подряд прежнее правило («оставить только
   имя файла») совпало 41 раз, это — 60 из 60.

   **Регистр.** Два пути, различающиеся только им, сводятся к первому
   написанию: диск сервера их различает, диск игрока нет, и дерево с такой
   парой доставить нельзя — проверка манифеста отвергает его как
   `duplicate path`.
5. **Чистка мусора** — рекурсивно, точное совпадение имени без учёта регистра:
   `CHANGELOG.md`, `icon.png`, `manifest.json`, `README.md`, `LICENSE`,
   `LICENSE.txt`. Затем удаление опустевших каталогов. Список — одна константа
   с тестом. `README.es.md` и подобные **не** трогаются.
6. **Публикация.** `scanManifest(filesRoot)` → `promoteVersionDir` →
   `writeManifest(updateLatest=false)`.
7. **Активация** — отдельной кнопкой, `writeLatestJSON`.

Шаги 6–7 — общий с играми код публикации; 1–5 написаны для модпаков.

### Импорт `mods.yml`

Тот же конвейер, но вместо резолва дерева от пакета-модпака список берётся из
`mods.yml` (или `.r2z`). Формат: блоки `- manifestVersion:` с полями `name`
(`Author-ModName`), `versionNumber: {major, minor, patch}`, `enabled`.
Выключенные моды пропускаются. Дальше — те же шаги 2–7.

Это путь миграции: из текущей сборки lethal-company получается модпак,
идентичный тому, что стоит у игроков.

## 7. Админка

Вкладка «Моды», модуль `server/admin_ui/mods-panel.js` — фабрика с поиском
элементов по `data-`атрибутам внутри своего корня, по образцу
`game-gallery.js`, а не по глобальным id: панель живёт на своей вкладке и не
должна конкурировать за имена с остальной админкой.

### Настройка игры

Выбор игры, слаг Thunderstore и кнопка **«Подтянуть из Thunderstore»**: она
читает ecosystem schema и заполняет `steamAppId`, `steamFolder`, `exeNames`,
`loader` и UUID раздела модпаков, показывая, что подставилось. Руками это не
набирается — ошибка в AppID или в имени папки обнаруживается только на машине
игрока.

Рядом ссылка **«Каталог на сайте»** — та же выборка на самом Thunderstore:
`/c/{community}/?ordering=most-downloaded&section={uuid}`. Именно UUID, а не
слаг: со слагом фильтр раздела молча не применяется.

Здесь же состояние кеша скачанных архивов и две кнопки — подмести по TTL и
очистить полностью.

### Собранные версии

Первым блоком, а не последним: список — то, ради чего вкладку открывают чаще
всего. Колонки: модпак и его версия, ссылка на страницу Thunderstore,
состояние, дата сборки, число модов, файлов и вес.

Бейджи говорят то, что иначе пришлось бы искать: **«активен»**,
**«доступна 2.2.13»**, если на Thunderstore вышла версия новее собранной,
**«пропущено N»**, если сборка шла без части модов, **«автор пометил
устаревшим»**. Действия: активировать, пересобрать под новую версию, дифф
состава с другой сборкой, удалить. Активную версию удалить нельзя, и
активировать её повторно тоже незачем — этих кнопок у неё просто нет.

Дифф читает пару `sources/{version}.json` и показывает добавленные, удалённые
и обновлённые моды.

### Сборка

Карточка появляется, когда сборка идёт, и показывает то, что происходит
прямо сейчас: разбор состава со счётчиком найденных модов, оценка размера,
скачивание (сколько пакетов и байт, сколько потоков в работе), установка,
чистка, подсчёт хешей. Отдельным свёрнутым списком — повторные попытки:
неудача, о которой никто не узнал, неотличима от зависания.

Поток событий читает `readNdjsonStream` из `ndjson.js` — общий модуль с
чанковой загрузкой сборок, а не третья копия того же цикла.

### Каталог модпаков

Поиск, сортировка (по умолчанию **most-downloaded**), пагинация. Карточка:
иконка, автор и название, описание, загрузки, оценки, когда обновлялся, бейдж
«устарел». Кнопки: **README**, **Состав** (разбор без скачивания — сколько
пакетов, вес, чего нет в наличии, хватает ли места) и **Собрать**.

Вес самого пакета в карточке НЕ показывается: в листинге это размер архива
модпака, а он почти пустой — 9 МБ у LethalReloaded против 1.8 ГБ настоящего
дерева. Настоящий вес появляется только после разбора состава, и до тех пор
честнее не показывать никакого.

README показывается **текстом**, а не разметкой: README чужих авторов полны
картинок и сырого HTML с чужого домена, и вставлять это одним `innerHTML` в
админку — приглашение к XSS.

### Куда идут запросы

Ни один запрос отсюда не идёт на thunderstore.io напрямую. Обёртка
`window.fetch` в `admin.js` переписывает пути и вешает CSRF, а обращение к
чужому хосту из браузера упёрлось бы в CORS и заодно утащило бы туда трафик
админки. Всё ходит через свой сервер: `/admin/mods/*`.

### Поля реестра

Блок `mods` записи игры хранится в реестре вместе с остальными полями и
приезжает в панель тем же `GET /admin/games`, что и список игр: слаг
сообщества сохраняется за игрой, и при следующем открытии вкладки каталог и
собранные версии подгружаются сами.

## 8. Публичный API

## 9. Клиент: синхронизация

Два независимых манифеста синхронизируются в **один** корень. Это требует
доработки движка синхронизации в трёх местах.

### Ограниченное удаление для модпака

Обычная синхронизация удаляет из корня всё, чего нет в манифесте. Для модпака
это снесло бы игру. Нужен режим, в котором список на удаление считается как

```
удалить = (пути ПРЕДЫДУЩЕГО манифеста модпака) − (пути НОВОГО манифеста модпака)
```

Предыдущий манифест хранится локально рядом с маркером версии. Если его нет
(первая установка) — удалять нечего.

### Защита файлов модпака от синхронизации игры

Симметрично: план синхронизации **игры** должен игнорировать пути, которыми
владеет модпак. Список берётся из установленного манифеста модпака, а не
захардкоживается: у разных игр в корень попадают разные папки данных модов
(`Mirage/`, `YPlayBoombox/`, `settings/` в реальной сборке lethal-company).

Реализуется через `PlanOptions`, а не новой глобальной константой в
`IsIgnoredRelFile` — иначе правило подействует и на играх без модов.

### Порядок синхронизации

**Сначала модпак, потом игра.** Это не косметика: при миграции файлы модов уже
лежат на диске с теми же хешами, поэтому синхронизация модпака скачает 0 байт
и запишет маркер, а синхронизация игры увидит их как «чужие» и не тронет. При
обратном порядке игра сначала удалит 5.8 ГБ, а модпак тут же скачает их заново.

### Маркеры версий

В корне игры два файла: `.version` (сборка игры, уже есть) и `.mods.version`
(модпак, новый). Оба в списке служебных файлов `IsServiceRelFile`, оба
исключены из обоих планов. Плюс `.mods.manifest.json` — копия установленного
манифеста модпака для ограниченного удаления.

### Что не трогаем

BepInEx пишет в свою папку во время работы. В исключениях синхронизации
модпака остаются:

- `BepInEx/cache/**` — пересобирается сам, удалять можно, но незачем;
- `*.log`, `BepInEx/LogOutput.log*` — **удалять нельзя**: лог нужен ровно
  тогда, когда игрок жалуется на вылет, и потерять его на обновлении обидно.

Конфиги (`BepInEx/config/**`) — обычные файлы манифеста, по принятому решению
обновление возвращает их к состоянию модпака.

### Проверка целостности

`IntegrityChecker` получает второй проход по манифесту модпака. Отчёт
показывает раздельно: файлы игры и файлы модов.

## 10. Клиент: запуск

| Вариант | Папка | `doorstop_config.ini` |
|---|---|---|
| Steam + моды | из Steam | `enabled=true` |
| Steam, ваниль | из Steam | `enabled=false` |
| Сборка + моды | `{GamesPath}\{gameId}` | `enabled=true` |
| Сборка, ваниль | `{GamesPath}\{gameId}` | `enabled=false` |

Кнопка «Играть» — split-button: основное действие это последний использованный
вариант, стрелка открывает список.

**Каждая строка доводит дело до конца сама.** Пункт меню, который ничего не
делает, — худший из возможных: «Steam · с модами» когда-то просто выключался с
припиской «моды не установлены — нажмите „Обновить“», причём «Обновить» на
карточке обновляет сборку с сервера и к копии из Steam отношения не имеет, а
настоящее действие пряталось в контекстном меню списка игр.

| Состояние | Что написано в строке | Что делает щелчок |
|---|---|---|
| всё на месте | `Steam · с модами (Lethal Reloaded 2.2.12)` | запускает |
| модов в копии нет | `— установить моды` | ставит и **сразу запускает** |
| моды устарели | `— обновить моды` | обновляет и запускает |
| Steam затёр загрузчик | `— восстановить моды` | ставит заново и запускает |
| сборки нет на диске | `— установить игру с модами` | ставит в очередь загрузок |
| сборка устарела | `— обновить` | ставит в очередь обновление |

Выключенной строка остаётся только тогда, когда сделать действительно нечего:
Steam не установлен, игра не куплена, модпак не собран — и тогда в строке
написано, почему.

Если сборки на сервере нет, вариантов **два**: такая игра живёт только копией
из Steam, и обещать «Сборку Chill Hub», которой негде взяться, незачем.

После установки модов игра запускается сразу — это минуты, и игрок выбирал
«играть». После скачивания сборки запуска нет: там гигабайты, к концу которых
человека перед лаунчером обычно уже не бывает.

Решения вынесены из страницы WPF в `Core/Mods/LaunchPlan.cs` (какие варианты
есть, что означает нажатие) и `LaunchRunner.cs` (сама цепочка) — внутри
страницы это код, который проверяется только руками, а ошибка здесь не падает,
а тихо делает не то.

### Поиск Steam-копии

`SteamLocator` идёт по ступеням:

1. реестр `HKLM\SOFTWARE\WOW6432Node\Valve\Steam` → `InstallPath`;
2. `steamapps\libraryfolders.vdf` → пути библиотек;
3. `appmanifest_{appId}.acf` → `AppState.installdir`;
4. `common\{installdir}`; если `steamFolder` начинается с `{installdir}/` —
   `common\{steamFolder}` (случай How To Fish).

Парсер VDF — свой, минимальный, не зависимость: формат простой, а тесты на обе
раскладки нужны в любом случае.

### Редактор `doorstop_config.ini`

Читает существующий файл, находит ключ `enabled` **тем регистром и с тем
оформлением, что в файле**, меняет только значение, пишет обратно атомарно.
Если файла нет — берёт шаблон из установленного модпака. Работает и с
Doorstop 3, и с Doorstop 4, потому что ничего не знает про имена остальных
ключей.

### Наигранное время

`Steam.exe -applaunch` завершается сразу, а `PlaytimeStore.BeginSession`
вешается на возвращённый процесс — метрика занулилась бы. Для Steam-варианта
лаунчер дожидается появления процесса по `exeNames` и следит за ним.

### Установка модов в Steam-копию

Отдельного пункта в контекстном меню нет: установка живёт строкой
«Steam · с модами» в меню кнопки «Играть» — у одного действия одно место.
Лаунчер синхронизирует манифест модпака в папку Steam, спросив перед этим
подтверждение: полтора гигабайта уезжают в ЧУЖУЮ установку, и человек должен
увидеть, в какую именно папку. Предупреждение остаётся: обновление игры в
Steam может удалить или сломать моды — после такого их ставят заново, и панель
сама предложит это строкой «восстановить моды».

## 11. Логи

Отдельный префикс `[mods]`. Каждая ступень, где что-то может пойти не так,
пишет результат:

- **Поиск Steam:** прочитан реестр → N библиотек → найден/не найден
  `appmanifest` → `installdir` → вложенность → итоговый путь. Пять ступеней,
  по логу видно, на какой сорвалось.
- **Синхронизация:** какой манифест, какой корень, план (скачать/удалить/
  оставить), сколько байт, сколько заняло.
- **Ограниченное удаление:** сколько путей в предыдущем манифесте, сколько
  удалено, сколько защищено от плана игры.
- **Правка ini:** путь, `enabled` до и после, найденный ключ.
- **Запуск:** способ (Steam/прямой), полная командная строка, рабочая папка,
  PID, для ванили — подтверждение, что моды выключены.
- **Метрики:** новые коды `mods_sync_failed`, `steam_not_found`,
  `doorstop_write_failed`, `mods_launch_failed` в `MetricsService.Error`.

## 12. Обратная связь

Логи уходят с каждым обращением — и с ручным, и с автоматическим отчётом об
ошибке. `Diagnostics.Build()` собирает хвосты `client*.log`, `boot*.log`,
`apply-update.log`, `FeedbackService` кладёт их в поле `logs`, сервер
принимает.

**Галочки «приложить диагностику» нет.** Раньше она была вместе со списком
того, что уйдёт, и это был выбор, которого у человека на самом деле не
существует: обращение «не запускается» без журнала не разбирается вовсе, а
отказ приложить его означает лишь, что ответа не будет. Форма переверстана в
тех же границах — модальный оверлей на главной, единая сетка с выровненными
метками, отступы из ресурсов темы.

Бюджеты бандла: `LogsTotalBudgetBytes` 512 КБ, `LogTailBytes` 128 КБ на файл.

**Секция `## Mods`** в бандле — то, без чего жалоба на моды не разбирается:
хвост `BepInEx/LogOutput.log`, `.mods.version`, `doorstop_config.ini` из папки
игры, дерево модов на два уровня, результат поиска Steam-копии со всеми
ступенями (реестр → библиотеки → `appmanifest` → папка).

**Со стороны админки** журнал скачивается отдельным файлом:
`GET /admin/api/feedback/logs?id={id}` отдаёт его как `text/plain` с
`Content-Disposition: attachment`. В карточке обращения показан хвост в 64 КБ и
полный объём рядом: бандл занимает до мегабайта, и вставлять его в страницу
целиком значит вешать панель ровно на том обращении, которое открыли потому,
что у человека что-то сломалось. Список обращений журналы не отдаёт вовсе —
только их размер.

**Лимит nginx проверять не нужно** — он с запасом. В `/feedback/submit` стоит
`client_max_body_size 3m` при серверном `MaxBodyBytes = 2·1 МиБ + 128 КиБ =
2.125 МиБ`, то есть nginx пропускает больше, чем принимает бэкенд, и слишком
большой отчёт отвергается внятным JSON, а не голым 413. Проверено на проде:
2.38 МиБ доходят до Go, 3.15 МиБ дают 413 от nginx.

> Сверяться нужно с `deploy-kit/nginx/sites/chillhub-launcher.conf`. В
> `build/deploy/launcher.conf` этого репозитория лежит копия конфига,
> оставшаяся от прежней схемы выкатки: она не обновляется, не отслеживается
> git и на момент написания отстала на одиннадцать месяцев — там всё ещё
> `2m`. Именно по ней и был сделан неверный вывод, что лимит надо поднимать.

## 13. Миграция существующих сборок

Затрагивает `lethal-company` и `risk-of-rain-2`. `drive-beyond-horizons` и
`peak` модов не содержат.

### Шаги

1. **Собрать модпак из `mods.yml`** текущей сборки. Для lethal-company это
   237 модов, 5.80 ГБ, все доступны. Результат — версия
   `r2modman-import-1.0.7` в состоянии «Собрана».
2. **Сверить.** Дерево, собранное нами, должно совпасть с `BepInEx/` в
   манифесте 1.0.7 по путям и хешам. Расхождения ожидаются только на мусорных
   файлах (`README.md` и прочие), которые r2modman оставляет, а мы удаляем.
   Отчёт сверки — часть шага, а не «посмотрели глазами».
3. **Выпустить чистую сборку игры** — 1.1.0 без `BepInEx/`, `winhttp.dll`,
   `doorstop_config.ini`, `.doorstop_version`, `mods.yml`, `manifest.json`,
   `Cache/` и папок данных модов.
4. **Активировать модпак**, затем активировать чистую сборку.
5. **Проверить на живом клиенте**, что переход стоит около нуля трафика.

### Почему переход почти бесплатный

Порядок синхронизации «сначала модпак, потом игра» означает: файлы BepInEx уже
лежат на диске игрока с теми же хешами, модпак их засчитывает и скачивает 0
байт, а чистая сборка игры их не трогает, потому что они принадлежат модпаку.
Скачивается только разница по файлам самой игры.

Если бы порядок был обратный — игрок скачал бы 5.8 ГБ заново.

### Сверка проведена

Автоматический тест `TestLiveMigrationLethalCompany`
(`server/internal/adminapi/mods/migration_test.go`, требует
`CHILLHUB_NET_TESTS=1`) сравнивает опубликованную сборку с тем, что соберётся
из её `mods.yml`. Прогон против прода:

```
в опубликованной сборке lethal-company 1.0.7: 220 папок модов в BepInEx/plugins
в mods.yml: 237 модов, включено 237
дерево из профиля: 237 пакетов, недоступно 0, загрузчик BepInEx-BepInExPack-5.4.2100
ИТОГ: совпало 220 из 220 установленных модов
```

Состав воспроизводится полностью. Разница между 237 в профиле и 220 папками в
`plugins` — это библиотеки, которые раскладываются в `patchers` и `core`, а не
в `plugins`; тест перечисляет их отдельным списком, и там ровно то, чего и
ждёшь (`HookGenPatcher`, `OdinSerializer`, `AsyncLoggers` и подобные).

Тест остаётся в наборе: он же проверит `risk-of-rain-2` и любую следующую
сборку, если поменять две константы вверху файла.

### Риск

Байтовое совпадение возможно, потому что моды берутся из тех же архивов тех же
версий. Но раскладка r2modman и наша могут разойтись в мелочах (порядок
схлопывания вложенных папок, регистр имён). Шаг 2 существует именно для того,
чтобы это обнаружить **до** выкатки, а не по жалобам.

### Что нашли живые сборки

Ни один из этих пунктов не был предусмотрен планом; каждый найден на реальном
модпаке и закрыт правкой с регрессионным тестом.

- **403 на длинном имени.** Угаданный адрес архива верен не всегда — см.
  раздел 6, шаг 3. Сборка вставала намертво на одном пакете.
- **Молчание вместо прогресса.** Разбор состава и смета занимают у большого
  пака около двух минут и не отчитывались вовсе; на экране это выглядело
  зависшей админкой.
- **Скорость.** Архивы качались по одному, темпом API. У хранилища появились
  своя очередь и свой темп, описания версий легли в кеш, а обход дерева
  переехал на индекс сообщества: минута превратилась в секунду.
- **Пространство имён с дефисом.** `swuff-star-…` разбиралось как команда
  `swuff`, получало `404` и объявлялось пропавшим с Thunderstore. Оператору
  предлагали собрать пак без двух модов, которые никуда не девались.
- **Схлопнутая вложенность.** Раскладка оставляла от пути только имя файла, и
  два разных файла мода превращались в один путь в двух написаниях —
  публикация падала на `duplicate path`. Правило исправлено и сверено с
  r2modman на 60 пакетах.
- **Обновление модпака не доезжало до игрока.** «Нужно ли обновление»
  считалось только по версии сборки игры, а активация модпака её не меняет:
  на карточке оставалось «Играть». Теперь сравниваются обе версии.

### Что осталось

- **Выпуск чистых сборок** — операционная работа на живом сервере. Сверка
  состава проведена и зафиксирована тестом (см. раздел 13); собрать модпак из
  `mods.yml` на проде, выпустить сборки игр без `BepInEx/` и переключить
  активные версии — работа в админке, а не в коде.

## 15. Тесты

Красный прогон останавливает выкатку — это гейт, а не украшение.

**Go.** Резолвер: транзитивный BepInEx (регрессия на How To Fish), удалённый
пакет, повтор `ns-name` с разными версиями, цикл, бэкофф при `429`,
пространство имён с дефисом, ответы из индекса сообщества и добор одиночными
запросами. Раскладка: каждый `trackingMethod`, схлопывание маршрута с
сохранением вложенности под ним, `config` без подкаталога, корень
пакета-загрузчика, сведение путей, различающихся регистром. Скачивание:
запасной адрес при `403`, повторы, отчёт о них в поток. Чистка: точные имена,
регистр, рекурсия, `README.es.md` не трогается. Парсер `mods.yml`: версии,
выключенные моды. Пути: `_mods` не выходит за корень, `games.Save` отвергает
`gameId` `_mods` и `_registry`. Кеш: TTL, вытеснение, ручная очистка.
Обращения: журнал отдаётся файлом, обращение без журнала даёт `204`, список
журналы не отдаёт.

**.NET.** Парсер VDF: обычный и вложенный `installdir`. Редактор ini: оба
формата оформления из реальных сборок, отсутствующий ключ, отсутствующий файл.
Ограниченное удаление: удаляет только выбывшие пути предыдущего манифеста.
Защита: синхронизация игры не удаляет `winhttp.dll`, `BepInEx/**` и папки
данных модов. Порядок: «моды → игра» при миграции даёт нулевой план загрузки.
Варианты запуска: все состояния строки меню (готово, поставить моды, обновить
моды, восстановить, установить игру, обновить сборку), «два варианта вместо
четырёх» без сборки на сервере, «Steam не найден», «модпак не собран».
Цепочка щелчка (`LaunchRunner`): запуск, очередь, вопрос перед записью в чужую
папку Steam, отказ, неудачная установка, повторный щелчок во время установки,
режим техработ по каждому действию отдельно. «Нужно обновление» при смене
только модпака. Сбор бандла с секцией Mods.

**JS.** `sectionFromHash` для `mods`, `readNdjsonStream` (частичные строки,
`\r\n`, обрыв потока), рендер каталога.

## 16. Риски

- **Объём.** LethalReloaded — 1.8 ГБ, текущий набор lethal-company — 5.8 ГБ.
  Кеш обязателен, проверка свободного места до начала скачивания — тоже.
- **Ограничение частоты Thunderstore** — измеренная проблема, не
  гипотетическая. Без бэкоффа сборка тихо выйдет неполной. Относится к API, а
  не к хранилищу архивов: пасти их одним темпом — потерянные минуты на каждом
  гигабайте.
- **Адрес архива угадывается** — закрыто: запасным адресом идёт
  `download_url` из метаданных, и пакет считается пропавшим, только когда не
  ответил ни один адрес.
- **Раскладка расходилась** с r2modman — найдено и закрыто: схлопывается
  маршрут, а не вложенность под ним, сверено на 60 пакетах подряд. Риск
  остаётся для игр с другими `installRules`: та же сверка нужна каждой новой
  игре.
- **Обновление игры в Steam** ломает моды. Показывать версию, под которую
  собран модпак, и предупреждать при расхождении.
- **Моды принадлежат папке.** Игра и в Steam, и в сборке — двойное место.
- **Античиты.** Для lethal-company, risk-of-rain-2 и how-to-fish неактуально;
  для будущих игр помечать вручную — в ecosystem schema такого поля нет.
- **Лицензии.** Зеркалирование чужих модов на свой сервер. Раздача приватная,
  но перепубликацию лицензии большинства модов не разрешают.
- **Утечка имени пользователя** в `mods.yml` старых сборок, раздаваемых
  публично. Закрывается перевыпуском сборок на этапе 6.
