## 1. Зачем

Сейчас моды зашиты внутрь сборки игры. Админ собирает набор модов в r2modman,
кладёт результат в ZIP вместе с игрой и публикует одной версией. Это значит:

- **обновить один мод = перезалить всю сборку** и заставить каждого игрока
  скачать разницу по всему дереву;
- **игру нельзя запустить без модов** — файлов ванильной игры отдельно нет;
- **Steam-копию модами не снабдить** — раздаётся только пиратская сборка целиком;
- **состав модов нигде не зафиксирован** машиночитаемо, кроме случайно
  попавшего в сборку `mods.yml` от r2modman.

После перехода сборка игры содержит только игру, модпак — только моды, и они
обновляются независимо.

`mods.yml` — экспорт профиля r2modman. В сборке lethal-company 1.0.7 он

Проверка доступности: **все 237 доступны сегодня**, суммарно **5.80 ГБ** в
архивах — ровно столько же, сколько занимает BepInEx в манифесте. Значит
текущий набор модов **воспроизводится из Thunderstore один-в-один**.

> `mods.yml` раздаётся публично по
> `https://launcher.samoy.love/content/lethal-company/1.0.7/files/mods.yml`
> и содержит путь `C:\Users\AlexeySamoylov\AppData\Roaming\r2modmanPlus-local\...`
> — имя пользователя Windows утекает наружу. После перехода этот файл в сборки
> не попадает (он в списке мусора), но старые версии стоит перевыпустить.

### Локальные установки

`D:\Games\Lethal Company` и `D:\Games\Risk of Rain 2` — BepInEx установлен
прямо в папку игры. `doorstop_config.ini`:

```ini
[General]
enabled = true
target_assembly=BepInEx\core\BepInEx.Preloader.dll
```

`.doorstop_version` = `4.5.0` и `4.0.0`. Путь относительный, аргументов
командной строки не требуется — игра запускается двойным кликом по exe и
подхватывает моды. **Это и есть штатный способ**, на нём строится весь план.

Форматирование ini у разных сборок разное (`enabled = true` против
`enabled=true`, слэши `\` против `/`) — редактор ini обязан править только
значение, сохраняя оформление файла.

### Thunderstore API

| Что | Эндпоинт | Проверено |
|---|---|---|
| Секции комьюнити (UUID) | `/api/cyberstorm/community/{slug}/filters/` | UUID секции **свой у каждой игры** |
| Каталог | `/api/cyberstorm/listing/{slug}/?section={uuid}&ordering={o}&q={текст}&page=N` | 20 на страницу |

| Версия | `/api/experimental/package/{ns}/{name}/{ver}/` | `dependencies[]` |
| README | `/api/experimental/package/{ns}/{name}/{ver}/readme/` | `{"markdown": "..."}` |

## 3. Принятые решения

| Решение | Выбор |
|---|---|
| Куда ставятся моды | **Прямо в папку игры**, рядом с файлами игры. Профиля нет |
| Как выключаются моды | Правка `enabled` в `doorstop_config.ini`. Аргументов не требуется |
| Конфиги модов | **Не сохраняются.** Обновление модпака возвращает настройки автора |
| Логи в обратной связи | Уходят **всегда**. Галочка и список удаляются, форма верстается заново в тех же границах |
| Кеш архивов на сервере | TTL **30 дней** по времени последнего обращения + ручная очистка |
| Что видит игрок | Название и версия модпака. Выбора нет |
| Зеркалирование | Моды скачиваются на сервер и раздаются с него |
| Один активный модпак | На игру — ровно один. Несколько собранных версий лежат рядом, активна одна |

## 4. Как работает установка модов

Никаких аргументов запуска, никаких абсолютных путей, никакого профиля.

```
D:\Games\ChillHub\lethal-company\        <- корень игры
├── Lethal Company.exe                   ─┐
├── Lethal Company_Data\                  │ манифест ИГРЫ
├── UnityPlayer.dll                       │
├── SteamFix64.dll                       ─┘
├── winhttp.dll                          ─┐
├── doorstop_config.ini                   │ манифест МОДПАКА
├── .doorstop_version                     │
└── BepInEx\                              │
    ├── core\BepInEx.Preloader.dll        │
    ├── plugins\Автор-Мод\*.dll           │
    └── config\*.cfg                     ─┘
```

`winhttp.dll` перехватывает загрузку процесса, читает `doorstop_config.ini`,
находит по относительному пути `BepInEx\core\BepInEx.Preloader.dll` и грузит
BepInEx. Всё внутри одной папки.

**Запуск с модами:** `enabled = true` → запустить exe (или Steam).
**Запуск без модов:** `enabled = false` → запустить exe. Файлы модов остаются
на диске, Doorstop их не грузит.

Из этого следует главное ограничение: **моды принадлежат папке**. Если игрок
хочет играть и в Steam-копию, и в сборку с сервера, модпак ставится в обе
папки и занимает место дважды. Лаунчер это поддерживает, но по умолчанию
ставит в ту папку, которую игрок выбрал последней.

### Как это делают другие менеджеры

Для справки, чтобы не повторять их ошибки:

- **r2modman** держит моды в отдельном профиле и передаёт
  `--doorstop-enable true --doorstop-target <абсолютный путь>`. Для ванили обе
  ветки шлют `--doorstop-enable false` — **флаг Doorstop 3**, который Doorstop 4
  (наш случай) не распознаёт.
- **r2modman для Epic/Xbox**, где аргументы до игры не доходят, правит
  `doorstop_config.ini`. Единственная его ветка, где выключение гарантировано.
- **Gale** для ванили просто не добавляет аргументы, но копирует `winhttp.dll`
  и ini в папку игры безусловно. Ваниль работает по промаху: в ini стоит
  `enabled = true` и относительный путь к preloader, которого в папке игры нет.

Наш способ — правка ini — совпадает с единственной надёжной веткой r2modman и
дополнительно переживает запуск игры мимо лаунчера, прямо из библиотеки Steam.

## 5. Сервер: модель данных

### Реестр игр

Новое поле в `games.Entry` (`server/internal/adminapi/games/games.go:26`):

```go
type Entry struct {
    // ...существующие поля
    Mods *ModsConfig `json:"mods,omitempty"`
}

type ModsConfig struct {
    Enabled       bool     `json:"enabled"`
    Community     string   `json:"community"`      // "lethal-company"
    EcosystemGame string   `json:"ecosystemGame"`  // ключ схемы; по умолчанию = Community
    SectionUUID   string   `json:"sectionUuid"`    // UUID секции "Modpacks", кеш из /filters/
    Loader        string   `json:"loader"`         // "bepinex"
    SteamAppID    string   `json:"steamAppId"`     // "1966720"
    SteamFolder   string   `json:"steamFolder"`    // "How to Fish/How to Fish"
    ExeNames      []string `json:"exeNames"`
}
```

Указатель, а не встроенная структура: у всех существующих записей поля нет, и
`omitempty` оставляет реестр байт-в-байт прежним.

**Осторожно:** `games.Save()` парсит payload обычным `json.Unmarshal` в
`Entry` — неизвестные ключи отбрасываются молча. Поле, добавленное только на
клиенте, тихо пропадёт. Заводить сразу с обеих сторон.

### Дерево на диске

```
content/manifests/_mods/{gameId}/{version}.json      манифест модпака
content/manifests/_mods/{gameId}/{version}.src.json  состав: пакет, дерево, время сборки
content/manifests/_mods/{gameId}/latest.json         активная версия
content/content/_mods/{gameId}/{version}/files/      готовое дерево модов
content/tmp/ts-cache/{full_name}.zip                 кеш архивов Thunderstore, TTL 30 дней
```

Имя версии — **`{ns}-{name}-{version}`**, например `ASTeam-LethalReloaded-2.2.12`.
Без имени пакета версии двух разных модпаков не упорядочены и путаются. Формат
проходит `adminutil.IsSafeVersion` (буквы, цифры, `-`, `_`, `.`). Пересборка
того же — суффикс `_2`.

`_mods` под `manifests/` — та же конвенция, что у существующего `_registry`.
Три правки:

- добавить в skip-список `games.FromManifests()` (`games.go:61`);
- добавить в скан-фолбэк `loadGamesByScanning()` в `server/cmd/api/main.go`;
- запретить `_mods` и `_registry` как `gameId` в `games.Save()` — сейчас
  `_registry` тоже можно завести игрой.

nginx менять не нужно: `location ^~ /content/` и `^~ /manifests/` уже
покрывают новые подкаталоги.

### `{version}.src.json`

```json
{
  "source": "thunderstore",
  "package": { "namespace": "ASTeam", "name": "LethalReloaded", "version": "2.2.12" },
  "packageUrl": "https://thunderstore.io/c/lethal-company/p/ASTeam/LethalReloaded/",
  "builtAt": "2026-08-27T12:00:00Z",
  "loader": { "package": "BepInEx-BepInExPack-5.4.2305", "doorstopVersion": "4.5.0" },
  "tree": ["BepInEx-BepInExPack-5.4.2305", "FlipMods-TooManyEmotes-2.3.17", "..."],
  "missing": [],
  "totalBytes": 1932735283
}
```

Нужен для диффа состава между версиями и для показа в админке. `source` может
быть `thunderstore` (пакет-модпак) или `r2modman` (импорт `mods.yml`).

## 6. Сервер: конвейер сборки модпака

Один NDJSON-поток, как у `UploadProcessStream`, чтобы админка показывала
прогресс на гигабайтах.

1. **Резолв дерева.** Обход в ширину по `dependencies`, первый встреченный
   `ns-name` побеждает. Параллелизм ≤ 4, бэкофф, повторы. `404` — «пакет
   удалён», строка в отчёте, не падение.
2. **Смета.** `HEAD` по CDN → суммарный вес. Сверка с `builds.FreeSpace`.
   Отдаётся **до** скачивания.
3. **Скачивание.** Прямо с `gcdn.thunderstore.io`, минуя редирект. Кеш по
   `{full_name}.zip` — версии иммутабельны.
4. **Раскладка** по `installRules` из ecosystem schema:
   - пакет из `modloaderPackages` → содержимое его `rootFolder` в корень;
   - `trackingMethod: none` (`config`) → без подкаталога;
   - `trackingMethod: subdir` → `BepInEx/<route>/{Author}-{ModName}/` со
     схлопыванием вложенных папок;
   - `subdir-no-flatten` → то же, но с сохранением структуры;
   - `*.mm.dll` → `monomod`; остальное → маршрут с `isDefaultLocation`.
5. **Чистка мусора** — рекурсивно, точное совпадение имени без учёта регистра:
   `CHANGELOG.md`, `icon.png`, `manifest.json`, `README.md`, `LICENSE`,
   `LICENSE.txt`. Затем удаление опустевших каталогов. Список — одна константа
   с тестом. `README.es.md` и подобные **не** трогаются.
6. **Публикация.** `scanManifest(filesRoot)` → `promoteVersionDir` →
   `writeManifest(updateLatest=false)`.
7. **Активация** — отдельной кнопкой, `writeLatestJSON`.

Переиспользуется всё начиная с шага 6. Новый код — шаги 1–5.

### Импорт `mods.yml`

Тот же конвейер, но вместо резолва дерева от пакета-модпака список берётся из
`mods.yml` (или `.r2z`). Формат: блоки `- manifestVersion:` с полями `name`
(`Author-ModName`), `versionNumber: {major, minor, patch}`, `enabled`.
Выключенные моды пропускаются. Дальше — те же шаги 2–7.

Это путь миграции: из текущей сборки lethal-company получается модпак,
идентичный тому, что стоит у игроков.

## 7. Админка

### Навигация

| Место | Что добавить |

Прятать секцию **только** классом `.hidden` — инлайновый `style="display:none"`
ломает `admin-dom.test.js:313`.

### Экран «Моды»

Слева — выбор игры (переиспользовать список из `game-list.js`), справа три
блока.

**Блок 1. Настройка игры.**

- переключатель «В игре есть моды»;
- слаг Thunderstore + кнопка **«Подтянуть из Thunderstore»** — читает
  ecosystem schema и заполняет `steamAppId`, `exeNames`, `steamFolder`,
  `loader`, `sectionUuid`, показывая, что подставилось;
- **ссылка «Открыть каталог на Thunderstore»** —
  `https://thunderstore.io/c/{community}/?ordering=most-downloaded&section={sectionUuid}`.
  Строится из закешированного UUID; со слагом фильтр молча не применится.

**Блок 2. Каталог модпаков** — новый модуль `mod-catalog.js` по образцу
`game-gallery.js` (фабрика + поиск элементов по `data-`атрибутам внутри root,
не по глобальным id).

- строка поиска (`q=`), переключатель сортировки (по умолчанию
  **most-downloaded**), пагинация;
- карточки: иконка, `автор/название`, описание, число загрузок, дата
  обновления, бейдж «устарел» при `is_deprecated`;
- кнопка **«README»** — модалка с рендером
  `/api/experimental/package/{ns}/{name}/{ver}/readme/`;
- кнопка **«Посмотреть состав»** — резолв без скачивания: сколько пакетов,
  вес, чего не хватает;
- кнопка **«Собрать»**;
- поле «или вставьте ссылку» — часть сборок не помечена категорией
  `modpacks` и в каталоге не находится.

Запросы к Thunderstore идут **через свой сервер** (`/admin/api/mods/catalog`),
не из браузера: обёртка `window.fetch` в `admin.js` переписывает пути и вешает
CSRF, а прямой запрос на чужой домен упрётся в CORS и утечёт наружу.

**Блок 3. Собранные версии** — `versionsTableHtml(items, latest, cls)` с новым
`cls`. Колонки: версия (`ASTeam-LethalReloaded-2.2.12`), ссылка на страницу
Thunderstore, статус, дата сборки, файлов, размер, действия
(«Активировать» / «Удалить»). Бейдж **«доступна 2.2.13»**, если на
Thunderstore вышла новая версия, и кнопка **«Пересобрать»**. Кнопка
**«Дифф состава»** — сравнение двух `{version}.src.json`: добавлены, удалены,
сменили версию.

`bindVersionActions` придётся обобщить: сейчас в неё зашиты URL
`/admin/activate?gameId=..&version=..`.

### Прогресс

Парсер NDJSON сейчас написан дважды внутри `runChunkedUpload`
(`admin.js:1733-1772`). Вынести в модуль `ndjson.js` с сигнатурой
`readNdjsonStream(res, onEvent)` по образцу `chunk-upload.js`, и использовать
из обоих мест. Разметку прогресса взять третьим ключом в `CARDS`
(`upload-card.js:29`) — тогда бесплатно приезжают `prog_wrap`, `pb`,
`prog_text`, `prog_pct`.

### Эндпоинты

Добавляются в `apiRoutes()` (`server/cmd/admin/routes.go:41`), алиас
`/admin/...` выводится автоматически:

```
POST /admin/api/games/ecosystem     подтянуть метаданные игры из ecosystem schema
GET  /admin/api/mods/catalog        каталог: gameId, q, ordering, page
GET  /admin/api/mods/readme         README пакета
POST /admin/api/mods/resolve        предпросмотр дерева
POST /admin/api/mods/build          сборка, NDJSON
POST /admin/api/mods/import         импорт mods.yml / .r2z, NDJSON
POST /admin/api/mods/activate       latest.json
POST /admin/api/mods/deleteVersion
GET  /admin/api/mods/list           версии + активная + доступное обновление
GET  /admin/api/mods/diff           дифф состава двух версий
POST /admin/api/mods/cacheClear     ручная очистка кеша архивов
```

### Поля реестра в UI

Новые поля добавлять **через `tr.dataset.<field>`** в `mgmAppendRow`
(`admin.js:1888`) и строкой в объекте `mgmSave` (`admin.js:2045`), по образцу
`pinned`/`unpublished`. **Не новой колонкой `<td>`**: `mgmSave`, `mgmReload` и
`game-list.js` читают колонки по жёстким индексам `tds[0..3]`.

Учесть: пин и drag-reorder в `game-list.js` зовут `window.mgmSave()`
немедленно, без подтверждения — черновик новых полей уедет на сервер вместе с
ними.

## 9. Клиент: синхронизация

Два независимых манифеста синхронизируются в **один** корень. Это требует
доработки движка синхронизации в трёх местах.

### Ограниченное удаление для модпака

Обычная синхронизация удаляет из корня всё, чего нет в манифесте. Для модпака
это снесло бы игру. Нужен режим, в котором список на удаление считается как

```
удалить = (пути ПРЕДЫДУЩЕГО манифеста модпака) − (пути НОВОГО манифеста модпака)
```

Предыдущий манифест хранится локально рядом с маркером версии. Если его нет
(первая установка) — удалять нечего.

### Защита файлов модпака от синхронизации игры

Симметрично: план синхронизации **игры** должен игнорировать пути, которыми
владеет модпак. Список берётся из установленного манифеста модпака, а не
захардкоживается: у разных игр в корень попадают разные папки данных модов
(`Mirage/`, `YPlayBoombox/`, `settings/` в реальной сборке lethal-company).

Реализуется через `PlanOptions`, а не новой глобальной константой в
`IsIgnoredRelFile` — иначе правило подействует и на играх без модов.

### Порядок синхронизации

**Сначала модпак, потом игра.** Это не косметика: при миграции файлы модов уже
лежат на диске с теми же хешами, поэтому синхронизация модпака скачает 0 байт
и запишет маркер, а синхронизация игры увидит их как «чужие» и не тронет. При
обратном порядке игра сначала удалит 5.8 ГБ, а модпак тут же скачает их заново.

### Маркеры версий

В корне игры два файла: `.version` (сборка игры, уже есть) и `.mods.version`
(модпак, новый). Оба в списке служебных файлов `IsServiceRelFile`, оба
исключены из обоих планов. Плюс `.mods.manifest.json` — копия установленного
манифеста модпака для ограниченного удаления.

### Что не трогаем

BepInEx пишет в свою папку во время работы. В исключениях синхронизации
модпака остаются:

- `BepInEx/cache/**` — пересобирается сам, удалять можно, но незачем;
- `*.log`, `BepInEx/LogOutput.log*` — **удалять нельзя**: лог нужен ровно
  тогда, когда игрок жалуется на вылет, и потерять его на обновлении обидно.

Конфиги (`BepInEx/config/**`) — обычные файлы манифеста, по принятому решению
обновление возвращает их к состоянию модпака.

### Проверка целостности

`IntegrityChecker` получает второй проход по манифесту модпака. Отчёт
показывает раздельно: файлы игры и файлы модов.

## 10. Клиент: запуск

| Вариант | Папка | `doorstop_config.ini` | Показывать, когда |
|---|---|---|---|
| Steam + моды | из Steam | `enabled=true` | найдена Steam-копия **и** модпак установлен в неё |
| Steam, ваниль | из Steam | `enabled=false` | найдена Steam-копия |
| Сборка + моды | `{GamesPath}\{gameId}` | `enabled=true` | сборка установлена **и** модпак установлен в неё |
| Сборка, ваниль | `{GamesPath}\{gameId}` | `enabled=false` | сборка установлена |

Кнопка «Играть» — split-button: основное действие это последний использованный
вариант, в списке только реально доступные.

### Поиск Steam-копии

Новый `SteamLocator`:

1. реестр `HKLM\SOFTWARE\WOW6432Node\Valve\Steam` → `InstallPath`;
2. `steamapps\libraryfolders.vdf` → пути библиотек;
3. `appmanifest_{appId}.acf` → `AppState.installdir`;
4. `common\{installdir}`; если `steamFolder` начинается с `{installdir}/` —
   `common\{steamFolder}` (случай How To Fish).

Нужен минимальный парсер VDF. Свой, не зависимость: формат простой, а тесты на
обе раскладки нужны в любом случае.

### Редактор `doorstop_config.ini`

Читает существующий файл, находит ключ `enabled` **тем регистром и с тем
оформлением, что в файле**, меняет только значение, пишет обратно атомарно.
Если файла нет — берёт шаблон из установленного модпака. Работает и с
Doorstop 3, и с Doorstop 4, потому что ничего не знает про имена остальных
ключей.

### Наигранное время

`Steam.exe -applaunch` завершается сразу, а `PlaytimeStore.BeginSession`
вешается на возвращённый процесс — метрика занулится. Для Steam-варианта
нужно дождаться появления процесса по `exeNames` и следить за ним.

### Установка модов в Steam-копию

Отдельное действие «Поставить моды в Steam-копию»: лаунчер синхронизирует
манифест модпака в папку Steam. Предупреждение: обновление игры в Steam может
удалить или сломать моды.

## 11. Логи

Отдельный префикс `[mods]`. Каждая ступень, где что-то может пойти не так,
пишет результат:

- **Поиск Steam:** прочитан реестр → N библиотек → найден/не найден
  `appmanifest` → `installdir` → вложенность → итоговый путь. Пять ступеней,
  по логу видно, на какой сорвалось.
- **Синхронизация:** какой манифест, какой корень, план (скачать/удалить/
  оставить), сколько байт, сколько заняло.
- **Ограниченное удаление:** сколько путей в предыдущем манифесте, сколько
  удалено, сколько защищено от плана игры.
- **Правка ini:** путь, `enabled` до и после, найденный ключ.
- **Запуск:** способ (Steam/прямой), полная командная строка, рабочая папка,
  PID, для ванили — подтверждение, что moды выключены.
- **Метрики:** новые коды `mods_sync_failed`, `steam_not_found`,
  `doorstop_write_failed`, `mods_launch_failed` в `MetricsService.Error`.

## 12. Обратная связь

**Логи уже отправляются.** `Diagnostics.Build()` собирает хвосты `client*.log`,
`boot*.log`, `apply-update.log`; `FeedbackService` кладёт их в поле `logs`;
сервер принимает (`feedback.Item.Logs`); автоотчёт `ErrorReporter` шлёт с
`includeDiagnostics = true`. Вызовов с `false` в проекте нет.

Доделать:

1. **Убрать галочку и список.** Удаляются `FbAttachDiagnostics`,
   `FbDiagnosticsToggle`, `FbDiagnosticsInfo`, обработчики
   `FbAttachDiagnostics_Click` и `UpdateFeedbackDiagnosticsInfo`, поле
   `BundleContents`. Никакой поясняющей фразы вместо них не остаётся.
   `FeedbackDraft.AttachLogs` фиксируется в `true`.
2. **Переверстать форму** в тех же границах (модальный оверлей на главной):
   заголовок, тип обращения, имя, контакт, текст, строка состояния, кнопки.
   Единая сетка с выровненными метками и полями, отступы из ресурсов темы, без
   магических `Margin`.
3. **Поднять бюджеты:** `LogsTotalBudgetBytes` 160 КБ → 512 КБ,
   `LogTailBytes` 48 КБ → 128 КБ.
4. **Добавить секцию `## Mods`** в бандл: хвост `BepInEx/LogOutput.log`,
   `.mods.version`, `doorstop_config.ini` из папки игры, дерево модов на
   2 уровня, результат поиска Steam-копии.
5. **Починить лимит nginx.** В `/feedback/submit` стоит
   `client_max_body_size 2m`, а сервер принимает
   `MaxBodyBytes = 2·1 МиБ + 128 КиБ ≈ 2.125 МиБ`. Полный бандл отвергается
   nginx-ом целиком — отчёт не обрезается, а **пропадает**. Поднять до `4m`
   в deploy-kit.

## 13. Миграция существующих сборок

Затрагивает `lethal-company` и `risk-of-rain-2`. `drive-beyond-horizons` и
`peak` модов не содержат.

### Шаги

1. **Собрать модпак из `mods.yml`** текущей сборки. Для lethal-company это
   237 модов, 5.80 ГБ, все доступны. Результат — версия
   `r2modman-import-1.0.7` в состоянии «Собрана».
2. **Сверить.** Дерево, собранное нами, должно совпасть с `BepInEx/` в
   манифесте 1.0.7 по путям и хешам. Расхождения ожидаются только на мусорных
   файлах (`README.md` и прочие), которые r2modman оставляет, а мы удаляем.
   Отчёт сверки — часть шага, а не «посмотрели глазами».
3. **Выпустить чистую сборку игры** — 1.1.0 без `BepInEx/`, `winhttp.dll`,
   `doorstop_config.ini`, `.doorstop_version`, `mods.yml`, `manifest.json`,
   `Cache/` и папок данных модов.
4. **Активировать модпак**, затем активировать чистую сборку.
5. **Проверить на живом клиенте**, что переход стоит около нуля трафика.

### Почему переход почти бесплатный

Порядок синхронизации «сначала модпак, потом игра» означает: файлы BepInEx уже
лежат на диске игрока с теми же хешами, модпак их засчитывает и скачивает 0
байт, а чистая сборка игры их не трогает, потому что они принадлежат модпаку.
Скачивается только разница по файлам самой игры.

Если бы порядок был обратный — игрок скачал бы 5.8 ГБ заново.

### Сверка проведена

Автоматический тест `TestLiveMigrationLethalCompany`
(`server/internal/adminapi/mods/migration_test.go`, требует
`CHILLHUB_NET_TESTS=1`) сравнивает опубликованную сборку с тем, что соберётся
из её `mods.yml`. Прогон против прода:

```
в опубликованной сборке lethal-company 1.0.7: 220 папок модов в BepInEx/plugins
в mods.yml: 237 модов, включено 237
дерево из профиля: 237 пакетов, недоступно 0, загрузчик BepInEx-BepInExPack-5.4.2100
ИТОГ: совпало 220 из 220 установленных модов
```

Состав воспроизводится полностью. Разница между 237 в профиле и 220 папками в
`plugins` — это библиотеки, которые раскладываются в `patchers` и `core`, а не
в `plugins`; тест перечисляет их отдельным списком, и там ровно то, чего и
ждёшь (`HookGenPatcher`, `OdinSerializer`, `AsyncLoggers` и подобные).

Тест остаётся в наборе: он же проверит `risk-of-rain-2` и любую следующую
сборку, если поменять две константы вверху файла.

### Риск

Байтовое совпадение возможно, потому что моды берутся из тех же архивов тех же
версий. Но раскладка r2modman и наша могут разойтись в мелочах (порядок
схлопывания вложенных папок, регистр имён). Шаг 2 существует именно для того,
чтобы это обнаружить **до** выкатки, а не по жалобам.

## 15. Тесты

Красный прогон останавливает выкатку — это гейт, а не украшение.

**Go.** Резолвер: транзитивный BepInEx (регрессия на How To Fish), удалённый
пакет, повтор `ns-name` с разными версиями, цикл, бэкофф при `429`.
Раскладка: каждый `trackingMethod`, схлопывание, `config` без подкаталога,
корень пакета-загрузчика. Чистка: точные имена, регистр, рекурсия,
`README.es.md` не трогается. Парсер `mods.yml`: версии, выключенные моды.
Пути: `_mods` не выходит за корень, `games.Save` отвергает `gameId` `_mods` и
`_registry`. Кеш: TTL, вытеснение, ручная очистка.

**.NET.** Парсер VDF: обычный и вложенный `installdir`. Редактор ini: оба
формата оформления из реальных сборок, отсутствующий ключ, отсутствующий файл.
Ограниченное удаление: удаляет только выбывшие пути предыдущего манифеста.
Защита: синхронизация игры не удаляет `winhttp.dll`, `BepInEx/**` и папки
данных модов. Порядок: «моды → игра» при миграции даёт нулевой план загрузки.
Выбор варианта запуска: 4 ветки плюс «Steam не найден» и «модпак не
установлен». Сбор бандла с секцией Mods.

**JS.** `sectionFromHash` для `mods`, `readNdjsonStream` (частичные строки,
`\r\n`, обрыв потока), рендер каталога.

## 16. Риски

- **Объём.** LethalReloaded — 1.8 ГБ, текущий набор lethal-company — 5.8 ГБ.
  Кеш обязателен, проверка свободного места до начала скачивания — тоже.
- **Ограничение частоты Thunderstore** — измеренная проблема, не
  гипотетическая. Без бэкоффа сборка тихо выйдет неполной.
- **Раскладка может разойтись** с r2modman. Ловится сверкой на шаге миграции.
- **Обновление игры в Steam** ломает моды. Показывать версию, под которую
  собран модпак, и предупреждать при расхождении.
- **Моды принадлежат папке.** Игра и в Steam, и в сборке — двойное место.
- **Античиты.** Для lethal-company, risk-of-rain-2 и how-to-fish неактуально;
  для будущих игр помечать вручную — в ecosystem schema такого поля нет.
- **Лицензии.** Зеркалирование чужих модов на свой сервер. Раздача приватная,
  но перепубликацию лицензии большинства модов не разрешают.
- **Утечка имени пользователя** в `mods.yml` старых сборок, раздаваемых
  публично. Закрывается перевыпуском сборок на этапе 6.
