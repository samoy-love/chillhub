# Установщик

`ChillHub-Setup.exe` собирается NSIS-скриптом `scripts/installer.nsi` через
`scripts/build-installer.ps1` — одинаково локально и в пайплайне. Установка
пользовательская: без прав администратора, по умолчанию в
`%LOCALAPPDATA%\ChillHub`.

## Имя на виду и имя в путях

Пользователю установщик представляется как **Chill Hub** (`APP_TITLE`):
заголовок окна, ярлыки, строка в «Установке и удалении программ», тексты
сообщений. По файловой системе и реестру по-прежнему ходит `ChillHub`
(`APP_NAME`) — `%APPDATA%\ChillHub`, `%LOCALAPPDATA%\ChillHub`, ключи
установки, `ChillHub.exe`. Разведены они не ради красоты: переименование
каталога данных отрезало бы конфиг и логи у всех, кто уже поставил лаунчер.

Ярлыки прежнего имени (`ChillHub.lnk` и папка `ChillHub` в «Пуске»)
установщик удаляет перед созданием новых, а деинсталлятор — вместе со своими:
иначе у тех, кто ставил старую сборку, осталась бы вторая, мёртвая пара.

## Тихая установка

```
ChillHub-Setup.exe /S /GAMESDIR=D:\Games\ChillHub /D=C:\ChillHub
```

| Ключ | Смысл |
| --- | --- |
| `/S` | без окон |
| `/GAMESDIR=<путь>` | папка для игр; она уезжает в `config.json` лаунчера |
| `/D=<путь>` | каталог установки |

`/D=` — требование NSIS: он всегда идёт **последним** и **без кавычек**, всё
после него считается путём. Пробелы в пути поэтому работают, а вот
процитировать его нельзя.

Без `/GAMESDIR` папка берётся из реестра прошлой установки, а если её нет —
`C:\Games\ChillHub` (или `D:\Games\ChillHub`, если диск D существует).

Что делает тихий режим, когда решение обычно принимает человек:

* установка **старее** уже установленной — отказ (откат версии скриптом почти
  всегда ошибка);
* файлы заняты запущенным лаунчером — отказ, а не ожидание у диалога;
* ярлык на рабочем столе — создаётся;
* удаление (`Uninstall.exe /S`) не трогает ни папку с играми, ни настройки.

Удаление из скрипта нужно запускать как `Uninstall.exe /S _?=<каталог>`: без
`_?=` деинсталлятор копирует себя во временный каталог и отдаёт управление
сразу, не дожидаясь конца работы. Плата за режим «на месте» — сам
`Uninstall.exe` остаётся, удалить работающий файл Windows не даёт.

Всё перечисленное проверяется на каждом прогоне CI:
`scripts/ci/smoke-installer.ps1` ставит установщик, сверяет результат и удаляет.

## Подпись

`ChillHub-Setup.exe` сейчас **не подписан**. Это видно каждому, кто скачивает
лаунчер с сайта: Windows показывает синий экран SmartScreen «Windows защитила
ваш компьютер», в свойствах стоит «Издатель: неизвестен», и чтобы поставить
программу, нужно нажать «Подробнее» → «Выполнить в любом случае». Часть
антивирусов относится к неподписанному NSIS-файлу тоже заведомо строже.

Чинится это не кодом: нужен сертификат подписи кода. Всё, что можно было
сделать заранее, уже сделано — шаг подписи встроен в
`scripts/build-installer.ps1` и включается переменными окружения. Пока их нет,
сборка идёт как раньше и печатает предупреждение, что артефакт не подписан.

### Как включить

| Переменная | Назначение |
| --- | --- |
| `CHILLHUB_SIGN=1` | включает шаг подписи; без неё шаг пропускается с предупреждением |
| `CHILLHUB_SIGN_THUMBPRINT` | отпечаток (SHA-1) сертификата в хранилище Windows |
| `CHILLHUB_SIGN_TIMESTAMP_URL` | сервер меток времени; по умолчанию `http://timestamp.digicert.com` |
| `CHILLHUB_SIGNTOOL` | путь к `signtool.exe`, если он не находится сам |

При `CHILLHUB_SIGN=1` без отпечатка сборка **падает**: молча не подписать
хуже, чем не собрать — выкатка иначе решит, что подпись есть.

После подписи запускается `signtool verify /pa`. Успех подписи не выводится из
кода возврата самой подписи: проверяется отдельно то, что получилось.

Метка времени ставится всегда и не отключается. Без неё подпись перестаёт быть
действительной в день истечения сертификата — включая **уже скачанные**
установщики, которые в этот день превратятся в «неизвестного издателя».

### Локально

```bash
CHILLHUB_SIGN=1 CHILLHUB_SIGN_THUMBPRINT=<отпечаток> pwsh ./scripts/build-installer.ps1 -AppVersion 1.5.11
```

Сертификат должен лежать в хранилище текущего пользователя или машины;
`signtool` найдёт его по отпечатку.

### В пайплайне

Сборка установщика идёт через `.deploy-kit/installer.env` (`BUILD_CMD`), а тот
вызывается из `deploy.yml` переиспользуемым workflow `desktop-artifact.yml` из
deploy-kit. Переменные окружения задаются там же, где `DEPLOY_VERSION`; секреты
репозитория (отпечаток) прокидываются через `secrets: inherit`.

Важно: пока `desktop-artifact.yml` не прокидывает `CHILLHUB_SIGN*` в окружение
шага сборки, включить подпись **только** правкой этого репозитория нельзя —
понадобится правка deploy-kit. Это единственный шаг, который здесь не сделан
заранее, потому что его нельзя ни написать, ни проверить не имея сертификата.

### Какой сертификат брать

Три варианта, по убыванию практичности:

1. **Azure Trusted Signing** (~10 $/мес). Подписывает в облаке, приватный ключ
   не покидает сервис, отдельного токена не нужно. Требует проверки
   организации либо индивидуального разработчика с историей ≥ 3 лет. Для
   личного проекта — самый дешёвый способ получить настоящую подпись.
2. **OV-сертификат** (~200–400 $/год, DigiCert, Sectigo и т. п.). С 2023 года
   ключ обязан лежать на аппаратном токене или в HSM, то есть подписывать из
   CI без облачного HSM неудобно.
3. **EV-сертификат** (~300–600 $/год). Отличается тем, что репутация
   SmartScreen выдаётся сразу, а не набирается загрузками. Для проекта с
   небольшим числом скачиваний это заметная разница: OV-подпись сама по себе
   убирает «неизвестного издателя», но синий экран может показываться, пока
   репутация не набрана.

Самоподписанный сертификат не даёт ничего: Windows ему не доверяет, и экран
SmartScreen остаётся на месте.
