# Соглашения репозитория

Правила одинаковы во всех проектах samoy.love. Файл лежит в корне каждого
репозитория — если правите его, правьте везде.

## Коммиты

**В коммитах не должно быть упоминаний ИИ.** Никаких трейлеров
`Co-Authored-By: Codex`, никаких «generated with» в сообщениях коммитов,
описаниях PR и релизных заметках. Это личные проекты и публичное портфолио —
авторство принадлежит владельцу репозитория.

Сообщения — на русском, повелительным наклонением, первая строка до 72
символов и без точки. Тело объясняет **почему**, а не пересказывает диф.

Первая строка коммита — это и есть строка релиза. Сквош-мерж схлопывает ветку
в один коммит, тема которого — заголовок PR, и именно её бот кладёт в чат при
выкатке. Больше о релизе читатель не увидит ничего, поэтому заголовок PR
подчиняется тем же правилам, что и тема коммита.

Тема отвечает, **что изменилось в проекте**, а не что изменилось в коде:
читатель в чате не видел ни ветки, ни дифа, ни задачи.

```
плохо   Заменить || true на разбор ответа в notify()
хорошо  Не выдавать недоставленное уведомление за успех

плохо   Убрать таймаут из HttpClientProvider
хорошо  Починить обрыв скачивания больших файлов

плохо   Правки после ревью
хорошо  Считать пропавший файл ошибкой обновления
```

Потолок темы — 120 символов: что длиннее, режется многоточием посреди фразы.
72 символа выше — норма, 120 — граница. Одна мысль — один коммит.

Тема читается в отрыве от всего: «Поправить как обсуждали», «Мелкие правки»,
«Фикс» в чате не значат ничего.

Тема не начинается с `WIP`, `fixup!`, `squash!`, `bump`, `deps: bump` и не
сводится к «Поднять версию» — генератор списка считает такое шумом и **молча
выбрасывает**. Настоящее изменение, названное так, из релиза исчезнет.

Темы коммитов **публичны**: они уезжают в `version.json`, который раздаётся
по HTTP, и в `summary.json` открытой статус-страницы. Ни секретов, ни
внутренних адресов, ни подробностей инцидента в теме.

Правило проверяется машиной, а не только совестью: задача `commits` в CI
валит сборку на любом упоминании ИИ. Локально то же самое ловит хук — он
включается один раз на репозиторий, клоном не переносится:

```bash
git config core.hooksPath .githooks
```

Не коммитим чужие изменения: перед коммитом смотрим `git status` и добавляем
только свои файлы. `git add -A` в грязном дереве запрещён.

## Ветки

Работа идёт в ветке, `main` защищён. Мерж — после зелёного CI.
Каждый мерж в `main` уезжает на прод, поэтому `main` обязан быть выкатываемым
в любой момент.

## Версии

Релиз без версии не едет. Версия проставляется до коммита, растёт явно и
проверяется после выкатки: `/version.json` на проде должен совпасть с тем,
что собрали. «Зелёный деплой со старыми файлами» ловится именно здесь.

## Выкатка

Единственный путь — [deploy-kit](https://github.com/tr0llex/deploy-kit).
Своих скриптов деплоя в проектах нет.

```bash
dk                 # что сейчас на проде
dk deploy          # выкатить цели этого проекта
dk rollback <цель> # откатить
```

Локальная выкатка и CI идут одним и тем же путём: одно описание цели
(`.deploy-kit/*.env`) и один `release.sh` на сервере.

## nginx

Конфигурация живёт **только** в `deploy-kit/nginx/`. В проектных репозиториях
копий не держим. Правки применяются через `server/nginx-apply.sh`, руками в
`/etc/nginx` не ходим.

## Тесты

Тесты — гейт, а не украшение: красный прогон останавливает выкатку.
У Go-сервисов обязателен `-race`. Покрытие уезжает в Codecov.

## Структура

```
README.md          русский, единственный markdown в корне вместе с
README.en.md       английской версией
README.<lang>.md   исключение: языковые версии README ищутся именно в корне
docs/              всё остальное, если нужно
.deploy-kit/       описания целей выкатки
.github/workflows/ вызовы переиспользуемых workflow из deploy-kit
```

Русский — основной язык: README.md русский, English идёт второй версией.
Порядок один во всех репозиториях, чтобы ссылка «Русский · English» вела
в одну и ту же сторону откуда угодно.

Журналы изменений в README не ведём — для этого есть история git.
Планы и идеи — в issues, а не в файлах.

# Chill Hub: команды и архитектура

Всё выше — общие правила samoy.love, они одинаковы во всех репозиториях.
Всё ниже — про этот проект; правки здесь никуда больше не переносятся.

## Команды

Нужны Go 1.26+, .NET 8 SDK, Node 24, PowerShell 7.

```powershell
scripts\run-dev.ps1     # api (:55700) + admin (:55777) + клиент, три окна
scripts\run-admin.ps1   # только админка
scripts\run-client.ps1  # только клиент
```

Перед пушем — ровно то, что гоняет CI (`.github/workflows/ci.yml`):

```bash
cd server && go vet ./... && go test ./... -race && golangci-lint run
cd ../launcher/tests/ChillHub.Tests && dotnet test
node --test tests/web/*.test.js          # из корня, нужен npm ci
```

Одиночные тесты:

```bash
go test ./internal/adminapi/builds -run TestUploadZip -race   # из server/
dotnet test --filter FullyQualifiedName~SyncFileRulesTests    # из launcher/tests/ChillHub.Tests
node --test tests/web/mods-panel.test.js                      # из корня
```

Линтеры (`make lint` = `lint-web` + `lint-go` + `lint-dotnet`) пинятся по
версиям в двух местах одновременно — `Makefile` и шапка `ci.yml`. Расхождение
означает «локально чисто, PR красный».

`dotnet format --verify-no-changes` — блокирующая проверка для четырёх
проектов: `launcher/ChillHub`, `launcher/tests/ChillHub.Tests`, `updater`,
`updater/tests/ManifestPreserveCheck`. Файлы `.cs`/`.xaml` прибиты к CRLF
через `.gitattributes` — иначе проверка выдаёт тысячи фантомных диффов.

Смоук по проду: `make smoke` (переопределяется `SITE_BASE=...`).
Выкатка — только `dk deploy`, цели описаны в `.deploy-kit/*.env`.

## Что где лежит

Четыре независимо выкатываемых куска, один домен `launcher.samoy.love`:

| Кусок | Код | Прод |
|---|---|---|
| Публичный API | `server/cmd/api` | `127.0.0.1:55700`, nginx `/api/*` |
| Админ-API | `server/cmd/admin` + `server/internal/adminapi/*` | `127.0.0.1:55777`, `/admin/api/*` |
| Морда админки | `server/admin_ui` (vanilla JS, без сборщика) | статика `/admin/ui/*` |
| Лендинг | `landing/` | корень `/` |

Клиент (`launcher/`, C# WPF, net8.0-windows, self-contained) к прод-серверу
не выкатывается: он приезжает установщиком NSIS (`scripts/installer.nsi`) и
обновляет себя сам.

Полная карта — `docs/spec.md`: §3.1 «консистентность путей» (кто какой путь
знает — установщик, клиент, API, nginx), §3.2 разбиение серверных пакетов,
§6 форматы манифеста/реестра/новостей, §8 эндпоинты админки.

## Инварианты, которые ломаются молча

**Три каталога клиента — разные и путать их нельзя.** `%LOCALAPPDATA%\ChillHub`
— установка (только файлы сборки), `%APPDATA%\ChillHub` — конфиг и логи,
`D:\Games\ChillHub` — игры. Конфиг, попавший в каталог установки, входит в
манифест самообновления, хеши не сходятся никогда — лаунчер обновляется вечно.
Тот же цикл ловится, если файл одновременно в манифесте лаунчера и под
preserve-правилами `updater/UpdatePreserve.cs`; детектор —
`updater/tests/ManifestPreserveCheck` (в CI гоняет самопроверку, против
настоящих манифестов запускается вручную с путём к `content/manifests/launcher`).

**Версия клиента живёт в `launcher/ChillHub/ChillHub.csproj` (`<Version>`) и
держится на шаг впереди прода.** Иначе локальная сборка считает себя устаревшей
и на старте уходит в окно самообновления.

**Себя лаунчер обновляет отдельным exe** (`updater/`) — запущенный процесс не
может переписать свои файлы.

**Маршруты админки объявляются один раз** в `apiRoutes()`
(`server/cmd/admin/routes.go`) под каноническим `/admin/api/...`; форма
`/admin/...` генерируется алиасом, кроме `noAlias` (вся `auth/*`, `upload/*`).

**Два фильтра путей в `deploy.yml` обязаны быть надмножеством друг друга** —
`on.push.paths` и job `changes`. Путь, попавший только во второй, отключает
выкатку цели молча. Сверяет `scripts/ci/deploy-paths-superset.py` (задача
`deploy-paths` в CI).

**Go-код проверяется на Linux и Windows.** `filepath.ToSlash` и файлы под
`//go:build !windows` расходятся между платформами беззвучно; прод — linux/arm64.

**`content/` не в git** (манифесты, файлы версий, новости, метрики, инбокс
обратной связи). Тесты, которым нужен контент, готовят его сами.

**Тесты лаунчера идут последовательно** (`xunit.runner.json`): тестируемый код
держит состояние в статике процесса — каталог логов, `ConfigService.Current`,
переменные окружения, файлы квот в `%APPDATA%`.

**Ничего не подписано** — решение, а не упущение; подлинность держится на TLS.
Установщик пользовательский, без прав администратора.

## Тексты для игрока

Всё, что видит игрок в лаунчере, — простым языком, без техжаргона и
ИИ-штампов. Тексты сообщений вынесены в отдельные классы
(`Core/Net/OfflineMessage.cs`, `Core/Home/HomeFormat.cs`, `Core/Game/…`) и
покрыты тестами — правьте текст там, а не в разметке.

Список обновлений (`Core/Changelog/ChangelogData.cs`) пишется ещё короче:
окно «Что нового» показывает всю историю разом, поэтому каждая лишняя строка
про вчерашнюю мелочь отодвигает важное. Выпуск называется результатом одной
фразой — «починена очередь загрузок», а не три строки про значки, объём и
падение. Потолок — три пункта на выпуск и 110 символов на пункт, и его
проверяет `ChangelogTests`.
